# R2Kernel™ 1.0.0

R2Kernel 1.0.0 is the first stable release of R2Kernel™. It fixes the public
vocabulary on Control, Procedure and Operation across the SDKs, the C ABI, the
configuration and the wire format; makes the C++ SDK match the Python SDK; sets
the C++ and C ABI baseline for the 1.x line; consolidates the public contract
dictionary; and removes the compatibility paths that existed only for earlier
prereleases. 1.0.0 is a stable release for functional development and for
deployments that do not depend on hard-real-time behavior. It is **not
qualified for hard-real-time operation**; see [Known limitations](#known-limitations).

These notes are complete for 1.0.0. The prerelease notes in the archive
describe those prereleases only.

## Supported use

- **Platforms.** Runtime bundles target Linux `x86_64` and `aarch64`; the
  documented installation path targets Ubuntu/Debian. A successful `aarch64`
  build is not evidence of native ARM execution, which has not been verified
  on `aarch64` hardware for this release. macOS and Windows are not runtime
  deployment targets. See [Installation](../getting-started/installation.md#supported-platforms).
- **SDKs.** The public subsystem-author SDKs are Python (`r2kernel-client`) and
  C++ (`libr2kernel_cpp`, CMake target `r2kernel::cpp`). They expose the same
  features with the same validation rules; the remaining naming differences are
  listed in the [SDK Reference](../reference/subsystem-sdk-reference.md). No
  other language SDK is published. The C ABI of the core library is the
  low-level interface the SDKs build on.
- **Managed execution** requires the Linux authority prerequisites, including a
  delegated cgroup v2 subtree and the supported process-creation and descriptor
  facilities. See [Resource Authority](../reference/resource-authority.md) and
  [Container Deployment](../operate/container-deployment.md).
- **Control.** Local Control uses protocol v5 over a Unix socket with shared
  memory for every payload. Host-to-host Control is best effort. There is no
  mixed-version fallback and no automatic replay of failed application effects.
- **Versions together.** Upgrade the runtime, the SDKs and every subsystem
  process together, and every host of a federation and of a PTP domain
  together.
- Tutorials and transport fixtures support functional development, not timing
  acceptance.

## Installation

1.0.0 supports **clean installs only**. The installer reads the release
recorded in an existing prefix and refuses to change it when that release is a
prerelease (for example `1.0.0rc11`) or when no final release version can be
read. Remove such an installation with its own uninstaller first, keeping a
copy of any configuration and credentials you want to reuse, then install 1.0.0
into the emptied prefix. Later final releases upgrade a 1.0.0 installation in
place. See
[Clean Installs And Upgrades](../getting-started/installation.md#clean-installs-and-upgrades).

A prerelease uninstaller can leave system state outside the prefix: the
resource authority policy, the `r2kernel` account and group, the
`r2kernel-device` group and udev rule, the package cgroup root and
`/run/r2kernel`. The 1.0.0 service installer retires that state when it can
prove that no installation uses it, and otherwise stops with the exact cleanup
commands. See
[State Left By A Prerelease Uninstaller](../getting-started/installation.md#state-left-by-a-prerelease-uninstaller).

The installer no longer accepts `--install-token`; a channel that needs an
install token reads it from `--install-token-file PATH` or
`R2KERNEL_INSTALL_TOKEN`.

## Changes since 1.0.0rc11

### Control, Procedure and Operation names

The SDKs, the C ABI, the configuration and the wire format use one vocabulary:
**Control** for timed request/response exchange, **Procedure** for calls and
**Operation** for long-running work with feedback. The older names are removed
without aliases.

| Area | 1.0.0rc11 | 1.0.0 |
| --- | --- | --- |
| Python client methods | `bind_timed_exchange`, `transact_timed_exchange`, `resolve_timed_exchange_target` and the other `*_timed_exchange*` methods | `bind_control`, `transact_control`, `resolve_control_target`, `*_control*` |
| Python handler contexts | `ServiceContext`, `TimedExchangeRequestContext`, `ActionContext` | `ProcedureContext`, `ControlRequestContext`, `OperationContext` |
| Python Operation helpers | `is_action_cancel_requested`, `publish_action_feedback`, `publish_action_result`, `publish_action_state`, `complete_action` | `is_operation_cancel_requested`, `publish_operation_feedback`, `publish_operation_result`, `publish_operation_state`, `complete_operation` |
| Python typed call | `call_typed_service` | `call_typed_procedure` |
| Python native client | `TimedExchangeRustClient` | `r2kernel.core.native_control.NativeControlClient` |
| C++ types | `TimedExchange*`, `Service*` and `Action*` types (for example `ServiceRequest`, `ActionContext`, `ActionStartOptions`) | `Control*`, `Procedure*` and `Operation*` types (`ProcedureRequest`, `OperationContext`, `OperationStartOptions`) |
| C++ request fields | `action`, `method` | `operation`, `procedure` |
| C ABI header | `r2kernel_core_timed_exchange.h` | `r2kernel_core_control.h` |
| C ABI functions and types | `r2kernel_timed_exchange_client_*`, `r2kernel_timed_exchange_server_*`, `R2KernelTimedExchangeClient`/`Server` | `r2kernel_control_client_*`, `r2kernel_control_server_*`, `R2KernelControlClient`/`Server` |
| C ABI codec | `r2kernel_codec_{encode,decode}_timed_exchange_{request,response}_v2` | `r2kernel_codec_{encode,decode}_control_{request,response}_v2` |
| Configuration section | `timed_exchange:` | `control_transport:` (same keys) |
| Error codes | `service_transport_failed`, `service_response_error`, `action_transport_failed` | `procedure_transport_failed`, `procedure_response_error`, `operation_transport_failed` |
| Request kinds | `service_request`, `action_start_request`, `action_cancel_request`, `action_query_request` | `procedure_request`, `operation_start_request`, `operation_cancel_request`, `operation_query_request` |
| Wire fields | `method` (Procedure name), `action` (Operation name) | `procedure`, `operation` |
| Control commands and topic | `resolve_timed_exchange_target`, `register_timed_exchange_handler`, `timed_exchange_hello` | `resolve_control_target`, `register_control_handler`, `control_hello` |
| Environment | `R2KERNEL_TIMED_EXCHANGE_REGISTRATION_CHECK_SEC` | `R2KERNEL_CONTROL_REGISTRATION_CHECK_SEC` |

Other observable names follow the same rule:

- Python results carry `procedure_response` instead of `service_response`;
  the Python Control error field `timed_exchange_status` is
  `control_channel_status`.
- Registration and route keys `timed_exchange_port`,
  `timed_exchange_local_*`, `timed_exchange_shm_*` and
  `timed_exchange_handler` are `control_port`, `control_local_*`,
  `control_shm_*` and `control_handler`.
- Status keys `timed_exchange_runtime_status`,
  `internal_runtimes.timed_exchange_runtime`, the `timed_exchange` section and
  `registered_timed_exchange_handlers` are `control_runtime_status`,
  `internal_runtimes.control_runtime`, `control_transport` and
  `registered_control_handlers`. The Console shows the group as
  "Control transport" and the runtime as "Control runtime".
- The local Control socket, the per-handler sockets and the shared-memory pool
  are named `r2kernel-control-local`, `r2kernel-control-handler` and
  `r2kernel_control_local` instead of their `timed-exchange` names.
- The SDKs no longer read `R2KERNEL_CONTROL_UNIX_SOCKET`, and the C++ SDK no
  longer reads `R2KERNEL_UNSAFE_ALLOW_DYNAMIC_ENDPOINTS`.

### Python SDK

- `current_control_source_authority()` and `current_protocol_host_authority()`
  report the authenticated transport context of the request being handled.
- The SDK reads `R2KERNEL_CONTROL_RT_MEMORY_BUDGET_BYTES`.
- The local Control handler socket defaults to mode `0660`
  (`R2KERNEL_RUNTIME_IPC_SOCKET_MODE` accepts one to four octal digits and
  refuses anything else).
- A process stopped by `SIGTERM` or exiting normally removes its local Control
  handler socket, as it already did its notification socket; before, a handler
  server stopped by `SIGTERM` left the socket in `/tmp`. Only the process that
  created the socket removes it: a forked child that stops an inherited client
  leaves the parent's handler socket in place.
- An Operation handler that is still running after `stop_operation_server()`
  ends normally when it returns; before, its worker thread failed with
  `task_done() called too many times`, and after a restart of the Operation
  server it could disturb the new work queue.
- SciPy is optional. The rotation and homogeneous-transform helpers in
  `r2kernel.utility.rotation_transform` need the `rotation` extra:
  `pip install 'r2kernel-client[rotation]'`.
- A lifecycle request names its transition only in `transition`, the member
  Control sends; the `action` fallback is removed.
- An Event subscription replays the publisher's bounded initial buffer only
  when Control reports that it preceded the publisher (`replay_existing`); a
  subscriber that joins later starts at the latest Event, as in the C++ SDK.
- `resolve_runtime_binding` returns "not ready" (`None`) for a restarted
  source that asks before its first status while its binding still names the
  previous registration (`registration_changed`), instead of raising.
- Removed: `r2kernel.utility.manipulator` (`find_tcp`, `find_payload`,
  `Palletizer2D`, `tooloffset_pose`), `r2kernel.helper.id`, the `UNIT` and
  `UNIT_TYPE` aliases, the GNSS and radar profile validators in
  `r2kernel.core`, and the re-export shims of moved modules. `offset_pose` and
  `blend_pose` are in `r2kernel.utility.common`.

### C++ SDK

The C++ SDK follows the Python SDK in features, signatures and validation.

**New in C++:**

- `ResourceBrokerClient` (UDP, TCP, frontend listener, CAN and device
  descriptors, inherited descriptors) and the matching `R2KernelClient::open_*`
  calls.
- `config_data`, `config_get`, `config_set`, `config_reload` and `config_save`
  on the same `<user_data>/config` YAML files as Python.
- `subsystem_manifest()`, `deployment_manifest()`, the public manifest model
  types and `load_subsystem_manifest`, `load_robot_platform_manifest`,
  `load_application_manifest`, `load_deployment_manifest` and
  `validate_required_bindings_for_subsystem`.
- Binding resolution: `launch_bindings`, `runtime_bindings`,
  `effective_bindings`, `resolve_binding`, `resolve_runtime_binding`,
  `binding_target` and `declared_runtime_endpoints`.
- `GatewaySubsystem` bound Control accessors (`bound_control_sessions`,
  `bound_control_authority`, `bound_control_owner`, `bound_control_session`)
  and `validate_control_authority`.
- `transact_bound_control`, `call_bound_procedure` and
  `start_bound_operation`, which spend one time budget on binding resolution
  and the call.
- `prepare_procedure`, `prepare_operation`, the timing header helpers,
  `lookup_frame_transform` and `spatial_status_payload`.
- The C++ SDK reads `R2KERNEL_STARTUP_REQUEST_TIMEOUT_MS`,
  `R2KERNEL_CONTROL_REGISTRATION_CHECK_SEC`, `R2KERNEL_CLOCK_STATUS_REFRESH_SEC`
  and `R2KERNEL_RUNTIME_IPC_SOCKET_MODE`.

**Changed signatures and behavior:**

- `bind_control(port, host)` returns the bound port and throws on failure.
- `resolve_control_target(target)` returns `std::optional<ControlRoute>`.
- `recv_control(target, type, timeout_ms)` takes the message type, and throws
  when a payload cannot be decoded.
- `configure_control_worker` takes the policy name (`OTHER`, `FIFO`, `RR`);
  `ControlWorkerStatus` reports `ready`, an optional `error` and `phase`.
- `bind_requirement` and `unbind_requirement` take an optional absolute
  deadline; without one each socket step has 1 s.
- `start_operation` uses the Python timeout default and wire form.
- `Subsystem::publish_event` has no priority argument; the registered priority
  applies.
- `declare_api_contract`, `declare_component` and
  `SubsystemOptions::declared_apis`/`declared_components` are removed. API and
  component declarations come only from the subsystem manifest, which is now
  always required.
- Manifests and deployments are validated with the same checks, in the same
  order and with the same error messages as Python (`ManifestError`):
  subsystem roles, requirements, provisions, exports, spatial declarations,
  robot slots, applications, deployment instances, bindings, Control binding
  groups and spatial topology. A deployment that the Python SDK or the CLI
  refuses is refused by the C++ SDK too.
- Manifest discovery follows Python: an explicit `manifest_path` is used
  instead of `R2KERNEL_SUBSYSTEM_MANIFEST`, and the deployment manifest is
  found through the option or `R2KERNEL_DEPLOYMENT_MANIFEST`, next to the
  subsystem manifest, its parent directory or the working directory.
- A `Subsystem` creates `<user_data>/config`, reads and validates the
  deployment manifest it finds, fails construction when a binding cannot be
  resolved, and starts in `WaitingBinding` when a required binding is missing.
- `SubsystemManifest::spatial_json` is `spatial`. `ProtocolHostAuthority`
  carries `kind` (`"protocol"`) as its first field, before `peer` and `epoch`.
- `ClockSource::R2KernelLogicalHw` has the value `5`.
- The local Control handler socket defaults to mode `0660` in every directory;
  in the system temporary directory it was `0666`.
- Every status carries `reported_lifecycle`, and non-native Control callers
  send the source-wrapped topic, as Python does.
- A Procedure or Operation request, response or query reply is read from its
  top-level members only. A Console or CLI call whose `params` contained a
  `request_id`, `target`, `timeout_ms` or endpoint name member no longer
  replaces the request's own value.
- A lifecycle request that Control sends without a reason has an empty
  `LifecycleTransitionRequest::reason` (it was the text `request_id`).
- A prepared Control route accepts a provider whose codec status Control has
  not received yet (`codec_context_available` is null) instead of failing with
  a yaml-cpp conversion error; an explicit `false` is still refused.
- `resolve_runtime_binding` returns no binding for a restarted source that
  asks before its first status while its binding still names the previous
  registration (`registration_changed`), instead of throwing.
- Operation feedback, result and state events use the Python SDK's binary
  event format, so C++ and Python providers and subscribers interoperate. A
  payload whose declared type (`feedback_type`, `result_type`, `state_type`) is
  a message is encoded with that type, as Python does; other payloads stay
  JSON.
- Operation events follow the Python provider. A terminal state event carries
  no payload, and the result follows in its own event only when there is one,
  so `fail()` without a payload publishes no result event. A cancel request,
  or `stop_operation_server()`, publishes a `cancel_requested` state event
  unless the Operation has finished. After a cancel request, only
  `cancel_requested` or a terminal state is published. A terminal state that
  the handler publishes itself ends the Operation: a value it returns or an
  exception it throws afterwards is neither stored nor published, and a cancel
  request or `stop_operation_server()` before the handler returns leaves it
  unchanged.
- `OperationEventMessage` adds `payload_type`, `payload_encoding` (`none`,
  `json`, `typed`, `raw`) and `payload_bytes`. A raw-bytes payload can now be
  told apart from a JSON string payload.
- Typed payloads can skip JSON. `OperationContext` publication and completion
  methods also take a `CodecByteView` already encoded with the declared message
  type, `OperationSubscribeOptions::payload_json = false` delivers typed
  payloads as bytes, and typed Procedures exchange encoded payloads
  (`ProcedureOptions::native_payload`, `ProcedureRequest::params_payload`,
  `ProcedureResponse::result_payload` and a `call_procedure` overload that
  takes bytes). A typed Operation event then costs about as much as a JSON one
  (tens of nanoseconds in process instead of about 0.8 to 2.3 microseconds),
  with the same bytes on the wire. The JSON APIs are unchanged.
- The Operation provider no longer publishes `queued` and `running` state
  events, as in Python; the start reply and queries still report them. An
  Operation canceled before its handler starts ends `canceled` without running
  the handler.
- `terminate()` and `stop_operation_server()` end running Operations as the
  Python `stop_operation_server()` does: 1 s to finish, then a cancel request
  with a `cancel_requested` state event for each unfinished one. Before,
  `terminate()` requested cancellation at once and published no event. A
  handler still running after its Operation finished sees the cancellation,
  but the Operation keeps its state.

**ABI:** `libr2kernel_cpp` is versioned `1.0.0` with SONAME
`libr2kernel_cpp.so.1`, and exports only the API marked public. 1.0.0 is the
ABI baseline of the 1.x line. Applications built against a prerelease C++ SDK
must be rebuilt.

### C ABI

- The header is `r2kernel_core_control.h`; the Control functions, types and
  envelope codec are renamed as in the table above.
- Removed exports: the version 1 envelope codec (the `_v2` codec accepts only
  version 2), the sender-based Control server receive/send pair (the
  token-based pair remains), the per-field shared-memory slot getters and
  setters and `write_payload`/`read_payload`/`write_typed` (use
  `publish`, `read_snapshot` and `reset_slot`), and
  `r2kernel_event_client_unsubscribe`. The federation apply report no longer
  has `subscription_ack_unsupported`.
- The library exports 90 symbols, all declared in the public headers. Code
  built against a prerelease header must be updated and rebuilt.

### Configuration

- **`control_transport:` replaces `timed_exchange:`.** Move the keys
  unchanged. A configuration (base, override or managed overlay) that still has
  a `timed_exchange` section fails to load, and `r2kernel config validate` and
  `r2kernel-config get`/`set`/`unset` refuse it; edit the file by hand. Unknown
  keys under `control_transport` are refused. See
  [Control Transport Settings](../operate/runtime-configuration.md#control-transport-settings).
- **Removed keys are refused at load:** `inline_payload_threshold`,
  `local_delivery_backend` and `windows_fallback_backend` (local Control always
  uses a Unix socket and shared memory), `control.web_terminal.allow_insecure_http`
  (Terminal follows the Console connection), `control.tcp_host`,
  `control.tcp_port`, and `port`/`tcp_port` in `federation.peers` entries.
- **`security.enabled: true` needs explicit `security.api` and `security.web`
  sections**, so the master switch never means "no authentication". The
  installed base configuration has both. See
  [Web and API Security](../operate/web-and-api-security.md#configuration).
- The resource authority policy requires `link_layer_grants`; the installer
  writes it.
- Control refuses to start while `R2KERNEL_CONTROL_VALIDATION_MODE` is set.

### Federation status

The unauthenticated federation status TCP listener and its plaintext fallback
are removed. Hosts exchange federation status only through the authenticated
Host API hello (`GET /api/v1/control/federation/hello`) at each peer's
`api_port`, under Host API authentication and `federation.security`.

- Each peer's `control.api_port` (default 8001) must be reachable from its
  peers. The former status port is no longer opened; remove it from firewall
  rules.
- A peer given as a plain host, or without `api_port`, uses this host's
  `control.api_port`; `api_port: 0` is refused. Runtime membership records and
  `PUT /api/v1/control/federation/peers` require `api_port`.
- Readiness no longer reports `core.tcp_ready`, and status no longer reports
  `control_ports.tcp` or per-peer `tcp_port`.
- Federation peers must request subscription acknowledgement, and Event frames
  must carry their published timestamp; frames without them are rejected.

See [Federation Security](../operate/web-and-api-security.md#federation-security).

### Control admission

Control requires from every client what the Python and C++ SDKs send: the
source-wrapped topic on local requests, `codec_metadata` before Control
requests and Event resources, `contract_codecs` on both sides of a typed
binding, and `reported_lifecycle` in every status. Registrations accept only
the `binary_shm_v5` local protocol. Clients that omit these are refused with an
explicit error. The status `notes` list is empty.

### Contracts and specs

- Contract IDs have no `r2kernel` authority segment. For example,
  `api.r2kernel.sensor.depth.source.v1` is `api.sensor.depth.source.v1` and
  `msg.r2kernel.depth.v1` is `msg.sensor.depth.v1`. Where an older contract
  overlapped (servo, timed digital output, camera source), the unprefixed ID
  keeps the newer definition: `api.actuator.servo.v1`,
  `api.io.digital.timed_output.v1`, `api.sensor.camera.source.v1`.
- The capability contract family is removed. Deployment planning refuses a
  robot `capabilities:` list, a `capability:` interface key and `capability.*`
  contracts. `Result` moves to `msg.core.common.result.v1`.
- Also removed: `msg.core.frame`, `msg.core.diagnostics`,
  `api.sensor.camera.v1` and `JointServoCommand`.
- Message-set files use the `version`/`id`/`kind: message_set` header, and a
  namespace `defaults.yaml` uses `kind: namespace_defaults` and lists every
  namespace. Runtime envelope messages are `msg.internal.*`.

See the [Spec Overview](../spec/spec-overview.md) and the
[API Contract Reference](../spec/api-contract-reference.md).

### Installer and runtime files

- The installer refuses prerelease and unknown-version installations (see
  [Installation](#installation)) and no longer migrates prerelease
  authentication, Console HTTPS, credential stores, site-packages or IPC pool
  permissions. The refusal is printed on standard error with a non-zero exit
  status before `sudo` is requested, also for an interactive run.
- The service installer retires host state that a removed prerelease provably
  left behind: it renames the old resource authority policy to
  `resource-authority.json.orphaned-<UTC time>` and adopts the `r2kernel`
  account and groups it proves R2Kernel's. A leftover `r2kernel-app` group
  without its account is adopted for the new package account when it is
  provably unused; otherwise the installer stops with the cleanup commands.
  Likewise a leftover `r2kernel-app` account whose primary group was deleted
  gets that group again with its GID (it no longer fails half-way or takes
  the `r2kernel` group as its primary group). In the adopted `r2kernel` group
  only the memberships of the new installation's accounts and manager user are
  carried over; other members, such as the manager user of the prerelease, are
  removed and named with the command that adds them back. Removing a
  membership does not change processes that already run: the installer names
  the running processes of such a user that still hold the group, and an
  account whose primary group is the adopted group. The orphaned state is
  described once, before any change.
- The installer checks its prerequisites (Python 3 with a working `venv` and
  `ensurepip`, and `sudo` for a non-root service install) before it creates
  the prefix or changes the system, and names the package to install, such as
  `python3-venv`.
- The installer records the group memberships it adds and the host state it
  creates. `r2kernel-uninstall` removes the resource authority policy, the
  package cgroup root, the udev device rule and the R2Kernel runtime entries in
  `/run`; with `--remove-users` it also removes the recorded memberships, such
  as the manager user in `r2kernel`, before it deletes the accounts and groups.
  A membership is removed only while the group still has the GID this
  installation created it with.
  It also removes an installation whose service registration failed before any
  unit was registered.
- Serial devices get their group back when R2Kernel is uninstalled. The
  installer records the owner, group and mode of the devices its udev rule
  changes, and `r2kernel-uninstall` restores them after removing the rule;
  for devices without a record it replays udev `add` events. Previously the
  devices kept the `r2kernel-device` GID after the group was deleted. While a
  device still has that GID, the uninstaller keeps the group, names the device
  and exits with status `3`. It also removes `/run/r2kernel-upgrade` when
  nothing else uses it, and with `--remove-users` the sudo timestamp records of
  the accounts it deletes. An install, upgrade or recovery that opened the
  coordination lock just before the uninstaller removed it opens the current
  lock again, so these coordinators still run one at a time.
- The installer accepts the relative library symlinks of the C++ SDK archive
  and refuses absolute links and links that leave the tree.
- The runtime IPC socket mode defaults to `0660` for the SDKs, Control and the
  installed services.
- The generated management TLS identity is
  `management-tls/device.certificate.pem` with `device.private-key.pem`; other
  certificate files are treated as custom certificates.

## Migration checklist for prerelease users

1. **Uninstall the prerelease.** Copy the configuration and credentials you
   want to keep, run `<prefix>/bin/r2kernel-uninstall`, then install 1.0.0.
   The prerelease uninstaller can leave the resource authority policy, the
   `r2kernel` account and group, the `r2kernel-device` group and udev rule, the
   package cgroup root and `/run/r2kernel`. The 1.0.0 service installer
   retires that state and adopts those accounts; when it cannot prove the state
   orphaned, it stops and prints the exact cleanup commands (see
   [State Left By A Prerelease Uninstaller](../getting-started/installation.md#state-left-by-a-prerelease-uninstaller)).
   Approve the device and link-layer grants of the old policy again; they are
   not carried over. The prerelease manager user's membership in `r2kernel` is
   not carried over either; add it back with `sudo gpasswd -a <user> r2kernel`
   if that user should keep access.
2. **Rename the configuration section.** Change `timed_exchange:` to
   `control_transport:` in every base, override and managed overlay file.
3. **Remove refused keys.** Delete `inline_payload_threshold`,
   `local_delivery_backend`, `windows_fallback_backend`,
   `control.web_terminal.allow_insecure_http`, `control.tcp_host`,
   `control.tcp_port` and peer `port`/`tcp_port`.
4. **Complete security sections.** With `security.enabled: true`, write both
   `security.api` and `security.web`.
5. **Open the Host API between federation peers.** Allow each peer's
   `control.api_port`, set `api_port` on peers whose Host API port differs,
   and close the former status port.
6. **Rename SDK code.** Apply the name table above to Python and C++ code,
   error-code checks and status or result parsing. Install the `rotation`
   extra if you use the rotation helpers.
7. **Rebuild C++ and C ABI consumers.** Include `r2kernel_core_control.h`,
   link the 1.0.0 `libr2kernel_cpp.so.1`, adopt the changed C++ signatures and
   replace removed C ABI calls.
8. **Update contract IDs and manifests.** Drop the `r2kernel` segment from
   contract IDs, move off capability contracts and removed messages, and make
   sure every C++ subsystem has a manifest that validates.
9. **Check custom clients.** Clients that do not use the SDKs must send the
   source-wrapped topic, codec identity, `reported_lifecycle` and the
   `procedure`/`operation` wire fields, and request subscription
   acknowledgement on federation sessions.
10. **Review socket permissions.** Subsystems that connect to local Control
    handler sockets need the owner or the IPC group (`R2KERNEL_RUNTIME_IPC_GROUP`,
    default `r2kernel`) under the `0660` default.

## Known limitations

- **No real-time qualification.** 1.0.0 is not qualified for hard-real-time
  operation, and there is no approved latency non-regression result for it.
  Finite measurements of the installed product on a host without CPU or IRQ
  isolation describe those conditions only: they are not WCET bounds and do not
  establish cross-host 1 kHz Control, physical-actuator completion or
  container behavior. Guest CPU affinity is not physical CPU or hypervisor
  isolation. Python is outside strict 1 ms periodic acceptance. The latency
  and throughput of same-slot named shared-memory synchronization are not
  measured.
- **Hardware verification.** `linux-aarch64` bundles are built but have not
  been run on `aarch64` hardware for this release. Following a PTP leader with
  a hardware clock under the standard PTP timescale has not been verified on
  hardware, and interoperation with third-party PTP hardware is untested; no
  hardware time-sync accuracy is claimed.
- **Time-sync supervisor.** If the time-sync supervisor is killed with
  `SIGKILL`, the kernel tick and frequency are not restored.
- **Shared trust is not tenant isolation.** Brokered CAN and UDP descriptors
  do not confine holders to the claimed adapter: CAN can be rebound and UDP can
  choose another adapter per datagram. Without brokered CAN sandboxing, Linux
  permits raw CAN sockets without a capability. Approved `CAP_NET_RAW` and
  `CAP_NET_ADMIN` are host-wide capabilities; declared protocols are labels,
  not enforced restrictions. Members of a shared IPC group or federation key
  are not mutually hostile tenants. Control authentication does not encrypt
  payloads or prove when a physical sample was produced.
- **Untrusted or slow file inputs.** Some package-supplied spec and Gateway
  contract reads lack file-type, size or execution bounds. FIFOs, devices or
  endless files may block or grow the reader, including validation of packages
  in `packages.additional_paths`. Blocking filesystem metadata can hold launch
  preparation capacity past the five-second reply deadline. The
  package-manifest size limit is not a sandbox for referenced files.
- **Retained state.** Package uninstall leaves instance runtime directories
  under `<prefix>/var/run/packages/<uid>/`; remove them only when no longer
  used. Failed or uncertain cleanup keeps ownership. Do not delete recovery
  state or relaunch to bypass a refusal.
- **Availability and diagnostics.** Event resource work can delay heartbeat
  and status, and a stalled resource service can keep handlers unavailable past
  SDK deadlines. Control has no Event topic-name length bound.
  Connection-admission overload can postpone federation readiness. Timing
  diagnostics can be incomplete; Event consumers must handle coverage gaps and
  overload.
- **WebSocket bounds.** The Event and Control WebSockets do not provide a
  general ping, idle-limit or send-timeout contract. Cookie session expiry does
  not supply those bounds for other authentication modes.
- **Named shared memory.** All participants of a named topic must run the same
  release; do not mix them with older binaries or with direct unsynchronized
  writers. Interrupted writes have no rollback. Do not reuse a shared-memory
  handle in a forked child.
- **C++ process and lifecycle.** A fork child must not use or destroy an
  inherited native client; use `exec` or `_exit`. A lifecycle dependency cycle
  across threads deadlocks and is not detected. `terminate()` is not
  async-signal-safe; call it before destroying the subsystem or anything its
  handlers use, and do not destroy a subsystem concurrently without it. An
  Operation handler that ignores cancellation blocks `terminate()`. A lifecycle
  status deferred to a heartbeat stopped by `terminate()` is not delivered.
- **Key rotation and Console.** Retiring a federation key pauses the affected
  Event traffic until the peer reconnects. The Web Console does not show
  instance link-layer status; use the package instance API.
