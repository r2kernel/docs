# R2Kernel™ 1.0.0rc8

!!! note "Prerelease archive"

    These are the notes of a 1.0.0 prerelease as published, kept for reference.
    They are not the current release. See [Releases](index.md) for the current
    release and its support, installation and limitation contract.

RC8 is an archived prerelease. Its artifacts and tags remain immutable.
This archive is not qualification for later releases. Use the
[current release notes](index.md) for current support. Upgrade the runtime
and SDKs together; local Control remains protocol v5 without mixed-version
fallback or automatic replay.

## Observable changes

- Native Event admission follows `disabled`, `optional` and `required` policy.
  Required mode does not accept plaintext or invalid registration proof.
  Plaintext compatibility does not disable Host API authentication or establish
  cryptographic authentication. Topic, codec, source-lifetime and freshness
  requirements remain applicable in every mode.
- Cross-host readiness requires sender and receiver observation, and clock
  checks on both hosts when requested. An old gate or sender-only topology is
  not receiver readiness, measured delivery, one-way latency acceptance or
  periodic performance qualification.
- Managed foreground completion requires whole-scope retirement, exact-child
  reap and resource release; incomplete cleanup is a failure retaining recovery
  identity. An ambiguous launch is not automatically resubmitted.
- Upgrade probes use the selected resource endpoint, not an unrelated default.
  Protected external HTTPS configuration can be inspected without granting
  permission to write or provision TLS outside the selected prefix.
- Uninstall uses selected protected configuration and ownership. External prefix
  consumers block removal. Dry-run does not mutate state and labels checks that
  can only be performed after service shutdown as deferred, not passed.

## Known historical limitations

Mixed Disabled/Optional Event delivery could depend on which host initiated the
connection. A publisher startup-order race could invalidate fixture readiness.
Whole-startup deadline/cancellation coverage and external HTTPS write-capability
reporting were incomplete. These were addressed in the successor release, not
by replacing RC8. Queued source-lifetime checks do not establish per-packet
application-session proof or physical production time.

## Qualification limits

Python is outside strict 1 ms periodic acceptance. Guest affinity does not prove
physical CPU or hypervisor isolation. No general WCET/hard-real-time, cross-host
1 kHz Control, physical-effect timestamp, hardware PTP or native ARM runtime
qualification follows from functional checks, build success or readiness.
Benchmark demos remain withdrawn.
